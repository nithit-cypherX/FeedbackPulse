# ตัวอย่างการอธิบายงานให้ต่อกันทั้งบท

อ่านเมื่อผู้ใช้ต้องการคำอธิบายหลายส่วนหรือให้เรียบเรียงบทความ ไม่ใช้เพิ่มความยาวให้คำตอบสั้น
ดูว่าคำถาม เหตุการณ์ ผล และข้อจำกัดต่อกันอย่างไร ไม่ต้องใช้หัวข้อหรือจำนวนย่อหน้าตามนี้
นี่เป็นตัวอย่างที่แต่งขึ้น ไม่ใช่ข้อความจาก Skooldio ผลตรวจโปรเจกต์จริง หรือหลักฐานว่า skill ได้ผลแล้ว
อย่านำตัวเลข สถานะ เหตุผล หรือชื่อฟีเจอร์จากตัวอย่างไปใช้แทนหลักฐานของงานอื่น

## Example evidence

โจทย์สมมติ: “ช่วยเล่างานสำรวจ Review & Merge ว่าทำไปทำไม เห็นอะไร และเกี่ยวกับงานเดิมอย่างไร”

กำหนดหลักฐานสำหรับฝึกเขียนดังนี้:

- ทีมเคยศึกษาข้อความ commit และขอให้ agent สำรวจข้อมูล review/merge ที่ทีมมีอยู่แล้ว
- Agent อ่านนิยามฟีเจอร์ โค้ดคำนวณ และรายงานเดิม ไม่ได้รัน extraction หรือฝึก classifier ใหม่
- โค้ดตรวจ review จากบัญชีอื่นเฉพาะ APPROVED/CHANGES_REQUESTED; จำนวน review นับ records ไม่ใช่บัญชีไม่ซ้ำ
- self-merge เปรียบเทียบบัญชีผู้เปิด PR กับผู้ merge; เวลา merge นับจากเปิด PR จน merge ไม่ใช่เวลาที่ลงมือทำงาน
- รายงานรวมทุกแหล่งข้อมูล ไม่ใช่ชุดทดสอบ classifier: กลุ่ม Human/AI มี median review records เท่ากับ 0/2 และ median เวลาถึง merge เท่ากับ 2/8 ชั่วโมง
- ข้อมูลหนึ่งแถวต่อ commit อาจซ้ำ PR เดิม; label อยู่ที่ commit ไม่ได้ยืนยัน label ของ PR ทั้งอัน ยังไม่ได้ตรวจผลแยกทุก repository หรือทดสอบว่าฟีเจอร์ช่วย classifier หรือไม่

## สิ่งที่ไม่ช่วยให้เรื่องต่อกัน

การเรียง “บริบท → นิยามทุกฟีเจอร์ → รายการข้อควรระวัง → ตาราง → สรุปข้อควรระวังอีกครั้ง”
ทำให้รายละเอียดครบได้ แต่ผู้อ่านยังต้องเชื่อมเองว่างานนี้กำลังตอบอะไร
ตัวอย่างข้างล่างเลือกอธิบายเฉพาะฟีเจอร์ที่ใช้เดินเรื่อง ไม่พยายามทำหน้าที่แทน feature dictionary

## ตัวอย่างคำตอบทั้งบท

### จากข้อความ commit ไปดูว่าใครตรวจงานก่อน merge

ที่ผ่านมาเราดูข้อความ commit เพื่อศึกษาว่าผู้เขียนอธิบายงานของตัวเองอย่างไร รอบนี้ทีมอยากตามต่อว่า หลังส่งงานแล้วมีใครเข้ามาตรวจ และงานถูกรวมเข้าโปรเจกต์อย่างไร ผมจึงสำรวจฟีเจอร์ Review & Merge และรายงานที่ทีมมีอยู่แล้ว เพื่อดูว่าข้อมูลส่วนนี้ช่วยตอบคำถามอะไรเพิ่มได้บ้าง

ลองนึกถึง PR หรือคำขอรวมโค้ดหนึ่งรายการ สมมติคุณเปิด PR แล้วเพื่อนเข้ามาตรวจและกดอนุมัติ ก่อนที่คุณจะกด merge เอง ถ้าดูแค่ว่าใคร merge เราจะยังไม่รู้ว่ามีเพื่อนตรวจงานให้แล้ว เพราะการตรวจงานกับการรวมโค้ดเป็นคนละขั้นตอน

ข้อมูลของเราจึงแยกดูสองการกระทำนี้ การตรวจจากบัญชีอื่นนับเมื่อมีผลอนุมัติหรือขอให้แก้ไข ส่วน self-merge ดูว่าผู้เปิด PR กับผู้ merge เป็นบัญชีเดียวกันหรือไม่ ในตัวอย่างเมื่อกี้จึงเป็นได้ทั้งสองอย่าง ถ้าเป็นเพียงคอมเมนต์โดยไม่มีผล review สองสถานะนั้น ก็จะไม่เข้าเกณฑ์แรก และในข้อมูลจริง บัญชีต่างกันไม่ได้ยืนยันว่าเป็นคนละคนเสมอไป [นิยามในโจทย์ตัวอย่าง](#example-evidence)

### พอดูรายงาน เราเห็นอะไร?

เมื่อแยกได้แล้วว่าใครตรวจกับใคร merge เป็นคนละเรื่อง คำถามถัดมาคือสองกลุ่มมีการตรวจมากน้อยและรอ merge นานต่างกันไหม รายงานเดิมมีตัวเลขให้เริ่มพิจารณาได้ดังนี้

ตารางนี้รวมทุกแหล่งข้อมูล และแบ่ง Human/AI ตาม label ของ commit ไม่ใช่ของ PR ทั้งอัน ข้อมูลเก็บหนึ่งแถวต่อ commit ดังนั้น PR ที่มีหลาย commits อาจถูกนับซ้ำ อย่าอ่านตัวเลขนี้เป็นผลเปรียบเทียบ PR ที่ไม่ซ้ำ

| ค่ามัธยฐานที่รายงาน | Human | AI |
| --- | --- | --- |
| จำนวน review records | 0 | 2 |
| เวลาจากเปิด PR จน merge | 2 ชั่วโมง | 8 ชั่วโมง |

ที่มา: [รายงานที่กำหนดไว้ในโจทย์สมมติ](#example-evidence) เป็นตัวเลขเดิม ไม่ใช่การคำนวณเพิ่ม

ในตารางนี้กลุ่ม AI มีค่ามัธยฐานของจำนวน review records และเวลาถึง merge สูงกว่า แต่จำนวน review เป็นจำนวนครั้งที่บันทึกไว้ คนเดียวตรวจหลายครั้งได้ จึงยังอ่านว่า “มีคนตรวจมากกว่า” ไม่ได้ ส่วนเวลา 8 ชั่วโมงรวมเวลารอด้วย ไม่ได้หมายความว่าผู้เขียนใช้เวลาลงมือทำงาน 8 ชั่วโมง

### แล้วข้อมูลนี้ช่วยงานเดิมตรงไหน?

ข้อมูลนี้ทำให้เราศึกษาได้มากกว่าว่าข้อความ commit เขียนอย่างไร: เราเริ่มถามถึงขั้นตอนที่งานผ่านก่อนถูกนำเข้าโปรเจกต์ได้ด้วย อย่างไรก็ตาม ตัวเลขยังไม่บอกว่าทำไมจึงต่างกัน เช่น จะสรุปว่า reviewer ไม่ไว้ใจ AI จากจำนวน review อย่างเดียวไม่ได้ และยังไม่ได้ตรวจว่าความต่างเกิดในทิศทางเดียวกันภายในแต่ละ repository หรือไม่

งานรอบนี้จึงได้ความเข้าใจว่านิยามฟีเจอร์วัดอะไร และมีผลเบื้องต้นอะไรให้ศึกษาต่อ จากการอ่านโค้ดกับรายงานเดิม ยังไม่ได้รัน extraction หรือทดสอบฟีเจอร์กับ classifier จึงยังตอบไม่ได้ว่าการเพิ่มข้อมูลกลุ่มนี้จะทำให้จำแนกได้แม่นขึ้น หากจะศึกษาต่อ ต้องแยกให้ชัดด้วยว่าเราต้องการอธิบายงานหลัง PR จบแล้ว หรือทำนายตั้งแต่ตอนเกิด commit เพราะตอนนั้นยังไม่มีข้อมูล review และ merge ที่จะเกิดตามมา

## ทำไมจึงจัดแบบนี้

- เปิดด้วยงานที่ทีมอยากเข้าใจและสิ่งที่ agent ทำ ไม่เริ่มด้วยวันที่ปรับหน้า หรือประกาศว่าจะจัดเนื้อหาเป็นกี่มุม
- ใช้ PR เดียวเชื่อมการ review กับ merge ก่อนแนะนำชื่อฟีเจอร์ แล้วจึงถามต่อถึงผลในรายงาน
- บอกขอบเขตข้อมูลติดกับตาราง เพราะถ้าแยกไปท้ายหน้า ผู้อ่านอาจเข้าใจผลผิด ส่วนชื่อฟังก์ชันและบันทึกการตรวจละเอียดไม่จำเป็นต่อเรื่องนี้
- ผลเชิงตัวเลข ข้อจำกัดการตีความ และสิ่งที่ยังไม่ได้ทดลองอยู่ในจุดที่ตอบคนละคำถาม ไม่ทวนข้อจำกัดชุดเดียวทุกหัวข้อ
- ลิงก์ในตัวอย่างย้อนกลับไปยังชุดหลักฐานสมมติเท่านั้น งานจริงต้องใช้แหล่งที่ตรวจจริงและระบุขอบเขตให้ตรง ไม่สร้าง citation เลียนแบบ

ก่อนส่งงานยาว ลองอ่านเนื้อหาต่อกันโดยไม่พึ่งหัวข้อ: ผู้อ่านรู้ไหมว่าทำไมย่อหน้าถัดไปจึงตามมา?
หากไม่รู้ ให้แก้ความสัมพันธ์หรือตัดส่วนเกิน ไม่ใช่เติมคำว่า “นอกจากนี้” หรือแต่งเหตุการณ์ให้ครบเรื่อง
ถ้าผู้ใช้ถามแค่ “self-merge คืออะไร” ให้ตอบเฉพาะจุดนั้น ไม่ผลิตบทความนี้ใหม่
