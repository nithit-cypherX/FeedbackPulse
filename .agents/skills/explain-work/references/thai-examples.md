# ตัวอย่างการอธิบายงานด้วยภาษาไทย

ใช้เทียบภาษาและการเชื่อมปัญหา การเปลี่ยนแปลง และผลที่เกิดขึ้น ไม่ใช่แม่แบบรายงาน
ทุกกรณีเป็นสถานการณ์สมมติเพื่อสาธิต ไม่ใช่ผลตรวจงานจริงหรือข้อความที่คัดจากบทความ
ในงานจริง ให้ยึดหลักฐานของงานนั้น อย่ายืมเหตุผล ตัวเลข ผลทดสอบ หรือสถานะจากตัวอย่าง

## น้ำเสียงที่ต้องการ

พูดเหมือนเพื่อนร่วมงานกำลังอธิบายงานให้ฟังอย่างสุภาพ บอกว่าส่วนไหนเปลี่ยนและเกี่ยวกับเป้าหมายอย่างไร
ศัพท์อย่าง validation, PR หรือ merge ใช้ได้เมื่อช่วยระบุสิ่งที่พูดถึง แต่ไม่ควรวางศัพท์ต่อกันแล้วให้คนอ่านแปลความเอง
ไม่ต้องเติมคำชม มุก คำขายของ หรือเรื่องเล่าประสบการณ์ที่ไม่มีหลักฐานเพื่อให้ดูเป็นมนุษย์

คำอย่าง “เพิ่มประสิทธิภาพ” หรือ “ยกระดับ” ไม่ใช่คำต้องห้าม แต่ต้องบอกได้ว่าอะไรเปลี่ยนไปจริง
หากยังไม่มีข้อมูล อย่าแต่งผลดีขึ้นมาแทนคำกว้าง ๆ นั้น
คำเชื่อมควรบอกเหตุผล ลำดับ หรือความต่างจริง ไม่ใช่ใช้ “นอกจากนี้” ต่อรายการงานที่ยังไม่สัมพันธ์กัน

## 1. บอกการเปลี่ยนแปลงแทนคำรายงานกว้าง ๆ

คำถาม: “ที่บอกว่ารวม validation นี่เปลี่ยนอะไร แล้วช่วยอะไร?”

หลักฐานสมมติ: เดิมหน้าสมัครสมาชิกกับหน้าแก้โปรไฟล์มีโค้ดตรวจอีเมลซ้ำกัน
แก้แล้วให้เรียกตัวตรวจอีเมลเดิมตัวเดียวกัน ไม่ได้เปลี่ยนกฎตรวจ และยังไม่มีผลวัดความเร็ว

ก่อน:

> ได้ดำเนินการรวมศูนย์ validation logic เพื่อยกระดับความสอดคล้องและลดภาระในการบำรุงรักษาระบบ

หลัง:

> ผมให้หน้าสมัครสมาชิกกับหน้าแก้โปรไฟล์ใช้ตัวตรวจอีเมลตัวเดียวกัน แทนการมีโค้ดตรวจแยกกันสองชุด
> กฎตรวจยังเหมือนเดิม แต่ถ้าจะเปลี่ยนกฎในอนาคตก็แก้ที่เดียว

จุดที่เปลี่ยน: ระบุสองหน้าที่ได้รับผลและสิ่งที่นำมาใช้ร่วมกัน คนอ่านจึงรู้ว่า “ดูแลง่ายขึ้น” หมายถึงอะไร
ไม่เปลี่ยนข้อสรุปเป็น “ระบบเร็วขึ้น” หรือ “ไม่มีบั๊กแล้ว” ซึ่งหลักฐานนี้ไม่ได้บอก

## 2. อธิบายหลายส่วนโดยผูกกับปัญหาเดียว

คำถาม: “ทำไมถึงแยกหน้า Explanation กับบันทึก Task แล้วผมควรอ่านหน้าไหน?”

หลักฐานสมมติ: เดิมทั้งสองหน้ามีทั้งบทเรียน ขั้นตอนทำงาน และผลตรวจซ้ำกัน
จัดใหม่แล้วให้ Explanation อธิบายหลักการ ส่วน Task เก็บสิ่งที่แก้และผลตรวจ พร้อมลิงก์หากัน
ยังไม่ได้ทดสอบว่าผู้อ่านหาคำตอบเร็วขึ้นหรือไม่

ก่อน:

> ปรับโครงสร้างเอกสารตามหลัก separation of concerns โดยแบ่ง conceptual layer และ execution record พร้อมเชื่อมโยงข้อมูลเพื่อเพิ่มประสิทธิภาพในการเข้าถึง

หลัง:

> เดิมสองหน้าเล่าทั้งหลักการและสิ่งที่ทำซ้ำกัน จึงแยกหน้าที่ให้ชัดครับ
> ถ้าอยากเข้าใจว่าระบบทำงานอย่างไร ให้อ่าน Explanation ส่วนถ้าอยากรู้ว่ารอบนี้แก้อะไรและตรวจได้ผลอย่างไร ให้อ่านบันทึก Task
> ผมใส่ลิงก์ระหว่างสองหน้าไว้แล้ว เพื่อให้เปิดดูรายละเอียดที่เกี่ยวกันได้โดยไม่ต้องเขียนซ้ำ

จุดที่เปลี่ยน: ใช้ปัญหาการอ่านซ้ำเป็นเรื่องหลัก แล้วอธิบายหน้าที่ของทั้งสองหน้าและเหตุผลที่เชื่อมกัน
คำตอบบอกวิธีเลือกอ่านได้ แต่ไม่อ้างว่าพิสูจน์แล้วว่าผู้อ่านเข้าใจหรือทำงานเร็วขึ้น

## 3. บอกผลตรวจและข้อจำกัดตรง ๆ

คำถาม: “ตอนนี้กันข้อมูลซ้ำได้แล้วใช่ไหม?”

หลักฐานสมมติ: รันเทสการส่งคำขอซ้ำทีละรายการแล้วผ่าน แต่ยังไม่ได้ทดสอบคำขอที่เข้ามาพร้อมกัน

ก่อน:

> ผลการตรวจสอบยืนยันความถูกต้องภายใต้ sequential execution แต่ยังไม่ครอบคลุม concurrent requests จึงไม่สามารถยืนยันกลไกป้องกันข้อมูลซ้ำได้อย่างสมบูรณ์

หลัง:

> กรณีส่งคำขอซ้ำทีละรายการ เทสผ่านแล้วครับ แต่ยังไม่ได้ลองส่งสองรายการพร้อมกัน จึงยังยืนยันไม่ได้ว่ากันข้อมูลซ้ำได้ในกรณีนั้น

จุดที่เปลี่ยน: บอกว่าตรวจอะไรแล้ว และยังสรุปอะไรไม่ได้ในประโยคที่ตามกันได้
ข้อจำกัดนี้มีผลต่อคำตอบ จึงต้องอยู่ตรงนี้ ไม่ซ่อนไว้ท้ายรายงานหรือส่วนกดเปิด
ไม่จำเป็นต้องขยายเป็นรายการข้อควรระวังทุกประเภท และไม่ใช่คำสั่งให้เริ่มทดสอบเพิ่มจากคำถามอธิบายงาน
