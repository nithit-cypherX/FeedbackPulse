## 1. ตรวจอะไร

หาว่า **การรัน evaluation ซ้ำให้ผลต่างกันเท่าไร** เพื่อใช้ค่านั้นเป็นเกณฑ์ตัดสินผ่าน/ไม่ผ่านตอนรันซ้ำในอนาคต · ค่านี้ต้องมาจากผลวัด ไม่ใช่ค่าที่ตั้งขึ้นว่าน่าจะพอ

## 2. วิธีวัด และเครื่องมือที่สร้างขึ้นเพื่อการนี้

### เพิ่ม fingerprint ของผลทำนายรายแถว

การเทียบ **confusion matrix หรือ metric รวมไม่เพียงพอ** — ผลรายแถวอาจต่างกันแบบหักล้างกันเองจนตัวเลขรวมยังตรง · `evaluate.py` จึงคำนวณ

```
predictions_sha256 = sha256( "<index>\t<sentiment>\t<repr(score)>\n" ทุกแถวตามลำดับ )
```

ใช้ `repr()` ของ score เพื่อเทียบถึง **ระดับ bit ของ float** ไม่ใช่ทศนิยมที่ปัดแล้ว · มี test ใน `tests/test_evaluation.py` ที่แสดงเคสที่ fingerprint มีไว้เพื่อจับ: ผลทำนายสองชุดที่ต่างกันทุกแถวแต่ได้ confusion matrix เดียวกัน

## 3. คาดหวังอะไร

ไม่มีค่าที่เอกสารกำหนดไว้ล่วงหน้า · คาดว่าผลควรเท่ากันเพราะ inference เป็น deterministic และไม่มีการสุ่มในขั้นตอนใด — [P02-T02](P02-T02-evaluation-dataset.md) ระบุว่า evaluation set คือทุกแถวในไฟล์ ไม่ sample ไม่ split จึง **ไม่มี random seed เข้ามาเกี่ยวข้องกับการเลือกแถว** · แต่ต้องวัดเพื่อยืนยัน ไม่ใช่สรุปจากเหตุผลนี้อย่างเดียว

## 5. Tolerance ที่กำหนด

กำหนดจากผลวัดข้างบน ไม่ใช่ค่าที่ตั้งขึ้น · **แยกตามเงื่อนไข เพราะหลักฐานครอบเงื่อนไขเดียว**

### เงื่อนไขที่วัดแล้ว — platform เดียวกัน, `uv.lock` เดียวกัน

| สิ่งที่เทียบ | Tolerance | ฐาน |
|---|---|---|
| `predictions_sha256` | **ต้องตรงทุก bit** | วัดได้ 0 ความต่าง ข้าม fresh-state rebuild |
| accuracy, macro-F1, macro precision/recall | **ต้องตรงทุก bit** | วัดได้ 0 ความต่างใน 5 รอบ |
| confusion matrix | **ต้องตรงทุกช่อง** | วัดได้ 0 ความต่างใน 5 รอบ |
| จำนวนแถวที่ข้าม | **ต้องเป็น 0** | วัดได้ 0 ทุกรอบ |
| เวลารัน | **ไม่ใช่เกณฑ์ตัดสิน** | ช่วง 4.8% ขึ้นกับภาระเครื่อง |

**ความต่างใดก็ตามในสี่แถวแรกถือเป็นสัญญาณที่ต้องสอบ ไม่ใช่ noise** · เหตุผลที่ตั้งเข้มได้คือ inference เป็น deterministic และไม่มีการสุ่มที่ไหนเลย ดังนั้นถ้าเลขขยับ แปลว่ามีอะไรเปลี่ยนจริง — เวอร์ชัน dependency, ไฟล์ model หรือโค้ด

### เงื่อนไขที่ยังไม่ได้วัด — platform อื่น

**ไม่กำหนด tolerance** เพราะไม่มีหลักฐาน · ทดสอบเพียงเครื่องเดียวคือ macOS 15.5 arm64

การเปลี่ยน CPU architecture, OS, build ของ `torch` หรือ BLAS backend เปลี่ยนลำดับการบวกทศนิยมได้ ซึ่งทำให้ logits ขยับในระดับ bit สุดท้าย และ `predictions_sha256` จะต่างทันทีแม้ sentiment ทุกแถวยังเหมือนเดิม · **นี่เป็นการให้เหตุผล ไม่ใช่ผลวัด** — เรายังไม่เคยรันบน platform อื่น

**คำแนะนำให้ P04:** ถ้า CI รันบน Linux x86-64 **อย่าใช้เกณฑ์ "ตรงทุก bit" เป็น gate ทันที** · ให้รันบน platform นั้นก่อนสองรอบเพื่อหาว่าค่าที่นั่นนิ่งแค่ไหน แล้วตั้งเกณฑ์จากผลนั้น · ถ้าพบว่า fingerprint ไม่นิ่งข้าม platform ให้ gate ด้วย sentiment ต่อแถวและ macro-F1 ภายใน epsilon ที่วัดได้ แทนการเทียบ bit

## 6. มีข้อจำกัดอะไร และส่งต่ออะไร

**ทดสอบ platform เดียว** — ข้อจำกัดที่ใหญ่ที่สุด ดังที่อธิบายในส่วนที่ 5

**fresh state ยังไม่สุด** — ลบ `.venv` และ HF cache แล้วติดตั้งใหม่จาก `uv.lock` และดาวน์โหลด model ใหม่ แต่**ยังใช้ Python interpreter ตัวเดิม** (`3.13.11` จาก Anaconda) และ `data/Tweets.csv` ไฟล์เดิม · ไฟล์ dataset มี `dataset.verify()` ตรวจ sha256 ทุกรอบอยู่แล้ว ส่วน interpreter ยังไม่ได้ทดสอบว่าเปลี่ยน patch แล้วผลเปลี่ยนไหม — [P02-T11](../docs/plans/P02-model-pipeline.md) pin ถึงระดับ minor เท่านั้น

**evaluation ประเมิน HF snapshot ไม่ใช่ชุด artifact ที่จะ deploy** — `evaluate.py` เรียก `ensure_model_files()` ซึ่งใช้ไฟล์จาก HF cache · [P02-T06](P02-T06-artifact-layout.md) ยืนยันแล้วว่าชุด artifact ให้ logits เท่ากันทุก bit บนข้อความจริง 300 แถว ดังนั้นผลใช้กับ artifact ได้**ผ่านความเท่ากันนั้น ไม่ใช่เพราะเป็นไฟล์เดียวกัน** · **เสนอให้พิจารณา:** เปลี่ยน `evaluate.py` ให้ประเมินจากชุด artifact โดยตรงจะปิดช่องนี้ แต่จะทำให้ T05 ขึ้นกับ T06 ซึ่งกลับลำดับ dependency ที่แผนวางไว้ — **ยังไม่แก้ ส่งเป็นข้อเสนอให้ทีม**

**ไม่ได้ทดสอบว่า tolerance นี้จับความผิดปกติได้จริง** — ยังไม่ได้ลองทำให้ผลเปลี่ยนโดยเจตนา (เช่น เปลี่ยนเวอร์ชัน `torch`) เพื่อดูว่าเกณฑ์จับได้ · การทดลองแบบนั้นใกล้เคียงกับงาน regression test ใน P05 มากกว่า

**ส่งต่อให้ P04:** ใช้ `predictions_sha256` เป็น gate ใน CI ได้ แต่ **ต้องวัดบน platform ของ CI ก่อนตั้งเกณฑ์** ตามส่วนที่ 5 · เวลารัน 650–680 วินาทีต่อรอบ ซึ่งอาจยาวเกินไปสำหรับทุก PR — พิจารณารันบน subset ใน PR และรันเต็มตอน release โดย**บันทึกว่า subset นั้นคือชุดใด** ไม่ใช่สุ่มใหม่ทุกครั้ง
