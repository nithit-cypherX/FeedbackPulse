## 3. เทียบสองทางเลือก

### ทางเลือก A — ใส่เข้า container image ตอน build (ที่เลือก)

artifact ถูก `COPY` เข้า image ตอน build แล้ว image ถูก push ไปที่ container registry

### ทางเลือก B — เก็บใน Blob Storage แล้วดาวน์โหลดตอน container เริ่ม

image ไม่มี artifact · container ดึง 477 MiB จาก blob ทุกครั้งที่เริ่มทำงาน

| เกณฑ์ | A — ใส่ใน image | B — ดาวน์โหลดตอน start |
|---|---|---|
| **bytes เดินทางเมื่อไร** | ไปกับ image ตอน pull | pull image **แล้วยัง**ต้องดึง artifact อีกต่อหนึ่ง |
| **ผลต่อ cold start** | artifact อยู่ใน image แล้ว เริ่มได้เลย · ขนาด image โตขึ้น 477 MiB | **ทุกครั้งที่เริ่ม**ต้องดึง 477 MiB เพิ่มจากการ pull image · [Proposal §3](../PROPOSAL.md#3-serving-pattern-and-requirements) ระบุว่า service **scale to zero เมื่อ idle** จึงเกิด cold start บ่อย |
| **rollback (R2)** | **ย้อนสิ่งเดียว** — image revision พา code + artifact ไปพร้อมกัน | **ย้อนสองสิ่ง** — image revision กับ pointer ที่ชี้ blob · ทั้งสองอย่างคลาดกันได้ |
| **งบ (Proposal §6)** | registry ที่สมมติไว้แล้วรองรับ · ไม่เพิ่ม egress นอกจากการ pull image | blob 5 GB ที่สมมติไว้แล้วรองรับ · **แต่เพิ่ม egress ทุก cold start** ซึ่งกินเข้า $3.55 ที่สำรองไว้สำหรับ "requests, network, operations" |
| **failure demo (R4)** | ต้องแก้ไฟล์ในคอนเทนเนอร์ที่รันอยู่ หรือ deploy image ที่พังตั้งใจ | **ง่ายกว่า** — ลบหรือเปลี่ยนชื่อ blob แล้ว readiness ต้อง fail |
| **เปลี่ยน model** | ต้อง build + deploy ใหม่ | เปลี่ยน config ชี้ blob ใหม่ |

### เหตุผลที่เลือก A

**1. รักษาการผูกที่ `model_version` อ้างไว้ให้เป็นจริง** — เหตุผลหลัก

[P02-T07](P02-T07-model-version-lineage.md) ออกแบบ `model_version` ให้ digest ครอบ **code commit + environment + artifact** พร้อมกัน เพราะ `predict()` ขึ้นกับโค้ดของเราไม่ใช่แค่ weights · ถ้า artifact อยู่ใน blob ที่สลับได้ตอน runtime **`model_version` จะอ้างการผูกที่ไม่มีอะไรบังคับ** — คนเปลี่ยน blob แล้ว API ยังคืน version เดิมได้ · การส่ง code กับ artifact ไปเป็น image ก้อนเดียวทำให้การผูกนั้นเป็นจริง

**2. rollback ย้อนสิ่งเดียว** — R2 ต้องพิสูจน์ว่า "rollback กลับรุ่นก่อนหน้าได้จริง" · ย้อนสองสิ่งที่คลาดกันได้คือความเสี่ยงที่ไม่ต้องรับ

**3. ไม่จ่ายค่าดึง artifact ซ้ำทุก cold start** — Proposal §3 เลือก scale to zero เอง ดังนั้น cold start ไม่ใช่กรณียกเว้น · ทางเลือก B ทำให้ทุก cold start มีงาน network เพิ่มที่ A ไม่มี

**4. artifact เป็น immutable เข้ากับ `artifact_id` ที่ content-addressed** — ของที่อยู่ใน image แก้ไม่ได้จากภายนอก

### สิ่งที่แลกไป — บันทึกไว้ตรงๆ

- **image โตขึ้น 477 MiB** → การ pull image ตอน cold start หนักขึ้น · **P04 ต้องวัด** ว่ากระทบ cold start เท่าไร
- **เปลี่ยน model ต้อง build ใหม่** ไม่ใช่แก้ config — ช้ากว่าแต่ตรวจสอบได้มากกว่า
- **failure demo ของคนที่ 3 ต้องเปลี่ยนวิธี** จากลบ blob เป็นแก้ไฟล์ในคอนเทนเนอร์หรือ deploy image ที่พังตั้งใจ · ดูส่วนที่ 5

## 4. ผล Check — ทางเลือกที่เลือกรองรับชุด artifact จาก T06 ได้

Check ของ T10 คือ "มีการตัดสินที่บันทึกแล้ว และทางเลือกที่เลือกรองรับชุด artifact จาก T06 ได้"

| ตรวจ | ผล |
|---|---|
| ชุด artifact เป็น directory ของไฟล์ธรรมดา `COPY` เข้า image ได้ | 6 ไฟล์ ไม่มี symlink ไม่มี sparse file ([P02-T06](P02-T06-artifact-layout.md)) |
| loader รับแค่ path ในเครื่อง ไม่ต้องต่อ network | **ยืนยันแล้วใน [P02-T06](P02-T06-artifact-layout.md)** — โหลดสำเร็จโดยตั้ง `HF_HOME` ชี้ไป directory ว่างและเปิด `HF_HUB_OFFLINE=1` |
| ไม่ต้องมีโค้ดติดต่อ cloud ใน core | `inference.py` ไม่มี `azure`/`boto`/`blob`/`requests` เลย |
| ขนาดพอดีกับงบที่สมมติไว้ | 477 MiB เทียบ Basic container registry ที่ Proposal §6 สมมติไว้แล้ว |

**สิ่งที่ยังไม่ได้ตรวจและไม่ใช่งานของ P02:** การ build image จริงและรันในคอนเทนเนอร์ · `Dockerfile` อยู่ใน non-goals ของ P02 และเป็นงาน **P03–P04**

## 5. ส่งต่ออะไร

### ให้ P04 (คนที่ 2) — สูตรแทนค่า ไม่ใช่ตัวเลขที่เดา

เวลา cold start ที่เพิ่มจาก artifact = **477 MiB ÷ throughput ที่วัดได้**

| ถ้า throughput ที่วัดได้ | artifact เพิ่มเวลา |
|---|---|
| 50 MiB/s | 9.5 s |
| 100 MiB/s | 4.8 s |
| 200 MiB/s | 2.4 s |
| 500 MiB/s | 1.0 s |

ตารางนี้เป็น**เลขคณิตจากขนาดที่วัดแล้ว** ไม่ใช่การอ้าง throughput ของ Azure ที่เราไม่ได้วัด · **P04 วัด throughput จริงแล้วแทนค่า**

สิ่งที่วัดในเครื่องได้คือ อ่านไฟล์ 477 MiB จาก page cache ที่อุ่นแล้วใช้ **0.10–0.15 วินาที** · ใช้ได้อย่างเดียวคือเป็น**ขอบล่างสุด** — การขนผ่าน network เร็วกว่าการอ่านจากเครื่องตัวเองไม่ได้ · แปลว่าเวลาที่เพิ่มขึ้นมาจาก network แทบทั้งหมด **ไม่ใช่การประมาณเวลาดาวน์โหลด**

รายการที่ P04 ต้องตัดสินและยังเปิดอยู่ใน P01-T03 §12: **จำนวน CPU/RAM** (ใช้ตัวเลขจาก [P02-T09](P02-T09-load-and-memory.md): sizing ที่ ~750 MiB ไม่ใช่ 341 MiB) และ **จำนวน process/instance**

### ให้คนที่ 3 (P05) — วิธีสาธิต failure เปลี่ยนไป

ทางเลือก A ทำให้ **ลบ blob ไม่ได้** เพราะไม่มี blob · วิธีที่ทำได้กับ A:

- แก้หรือลบไฟล์ใน `model/` ของคอนเทนเนอร์ที่รันอยู่ แล้วให้ readiness fail เมื่อ restart — ใกล้เคียง disk corruption ที่เกิดได้จริง
- deploy image ที่ตั้งใจใส่ artifact ที่พัง

`manifest.json` มี sha256 ของทุกไฟล์ให้ตรวจความครบถ้วนได้ **แต่การเรียกตรวจตอน startup เป็นของ P03** และการตัดสินว่าอะไรนับเป็น "artifact ใช้งานไม่ได้" เป็นของ P05 — P02 ผลิตข้อมูลให้แล้วแต่ไม่เขียนฟังก์ชันตรวจไว้ล่วงหน้า

## 6. ข้อจำกัดของการตัดสินใจนี้

**ตัดสินโดยไม่ได้ทดลองกับ Azure เลย** — ไม่มี `az` CLI และไม่มี credential ในเครื่อง และการสร้าง resource อยู่ใน P04 พร้อมเรื่อง credentials กับงบ · การตัดสินนี้จึงวางบนคุณสมบัติเชิงโครงสร้างและสมมติฐานงบที่ Proposal เขียนไว้เอง **ไม่ใช่ผลทดลองบน cloud**

**ยังไม่รู้ว่า Azure Container Apps cache image layer ระหว่าง cold start อย่างไร** — ถ้า cache ดีมาก ข้อดีของ A จะยิ่งชัด ถ้าไม่ cache เลย ทั้งสองทางเลือกจะใกล้กันขึ้น · **P04 ต้องตรวจ** และถ้าพบว่าสมมติฐานนี้ผิดอย่างมีนัยสำคัญ ให้กลับมาทบทวนการตัดสินนี้

**ไม่ได้เทียบทางเลือกที่สาม** เช่น Azure ML model registry หรือ volume mount · ตัดออกเพราะทั้งสองเพิ่มบริการที่ Proposal §6 ไม่ได้สมมติไว้ในงบ จึงต้องแก้ประมาณการงบก่อนจะพิจารณาได้
